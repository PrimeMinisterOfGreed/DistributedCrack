\section{Attacco con ricerca lineare}
Un attacco alle password, è abbastanza simile almeno in forma teorica, a un algoritmo di ricerca lineare di un elemento conosciuto in una lista. Infatti ,almeno nella sua forma più semplice , si può pensare al database come ad una lista di coppie utente-password, in cui si vuole cercare la presenza di un elemento conosciuto, cioè la password che correntemente si sta cercando di testare. Si supponga di avere N coppie utente-password e K password da testare, se si implementasse un algoritmo lineare sequenziale, la complessità in termini di tempo sarebbe $O(N*K)$, lo stesso in termini di spazio occupato, entrambi questi costi possono essere utilizzati come caso base per stimare una possibile ottimizzazione. 

\subsection{Ricerca Lineare con architettura main worker}
Dovendo effettuare una comparazione, si può distribuire il file con le password a tutti i nodi e dividere in P parti, quanti sono gli esecutori, il file del database. A questo punto idealmente  il file del database viene distribuito in modo statico, o in modo dinamico. Nel primo caso significa che all'inizio verranno trasmessi $(P*N)/P=N$ bytes per distribuire il database e $P*K$ per distribuire le password da testare, per poi cominciare ad eseguire gli $(N/P*K)$ confronti, in termini di complessità non ci si è allontanati molto dal caso base purtroppo, ma la cosa peggiore di questo metodo è che all'inizio presuppone di saturare molto l'I/O dei vari nodi per scambiarsi il file senza fare nient'altro, che può comportare uno spreco di tempo non indifferente. Nel secondo caso, la situazione migliora già notevolmente, ipotizzando un architettura main-worker infatti, il main divide il file in pezzi equi spaziati che i worker richiedono ogni volta che finiscono la computazione su uno, bisogna comunque distribuire all'inizio le copie delle password da testare, per cui la complessità computazionale e lo spazio occupato non cambiano rispetto al caso precedente, ma almeno la trasmissione del database e il confronto avverranno parallelamente.

Supponendo di aver completato la parte iniziale di scambio del file con le password da testare, rimane solo più il file del database, che può essere suddiviso e scambiato con i nodi su richiesta, sotto forma di Task. Ogni qualvolta il worker è vuoto chiede al nodo root un task, questo può essere o una coppia di indici, nel caso in cui ad esempio il file sia condiviso tramite clustered filesystem, oppure direttamente un array di stringhe qual'ora questo meccanismo non sia disponibile. Ogni qualvolta un worker trova una delle password nella porzione di file che gli è stata assegnata, questi lo notifica al nodo Root che rimane in attesa di questa tipologia di messaggi, e registra il risultato che alla fine della computazione verrà mostrato all'utente.

\subsection{Un architettura alternativa al main-worker}

Nel caso del main worker si è costretti a passare almeno uno dei due file in copie ai diversi nodi. A meno di non assicurarsi con metodi più o meno complicati, che ogni porzione del file di password sia stata comparata con ogni porzione del database in circolazione tra i nodi. In alternativa, si può adottare un'architettura a pipeline con topologia ad anello ($N \to N+1 \pmod{P}$). In questo modello, il dizionario delle password viene suddiviso tra i nodi, mentre i blocchi del database "scorrono" attraverso la pipeline. Ad ogni stadio, un blocco di dati viene confrontato con il set di password locale, realizzando un confronto completo dopo un intero ciclo della pipeline.
