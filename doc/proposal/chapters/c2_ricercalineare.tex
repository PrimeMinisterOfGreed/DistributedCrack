\section{Attacco con ricerca lineare}

In un attacco di tipo password spraying esistono due entità, il database e il file con le password da testare, che vanno confrontati tra di loro. L'operazione di confronto è molto simile a un operazione di ricerca, infatti il database può essere visto come una lista utente-passwordhash in cui si vuole controllare quali di questi hash sono contenuti nella lista delle password. Riassumendo le operazioni da fare in questo caso sono:
\begin{itemize}
    \item Caricare in memoria il file del database 
    \item Caricare in memoria il file delle password
    \item Calcolare l'hash della password correntemente in esame 
    \item Per ogni coppia nella lista del database controllare se esistono uno o più hash che corrispondono a quella password (al suo hash)
\end{itemize} 
Volendo si può scrivere in modo molto semplice in forma algoritmica 

\begin{lstlisting}
    database = load_database()
    passwords = load_passwords()
    foreach word in passwords do {
        pwhash = hash(word)
        if pwhash is in database{
            notify_password_found(word)
        }
    }
\end{lstlisting}

Da questa semplice forma algoritmica si possono estrarre diverse variabili, utili a stimare successivamente i tempi d'esecuzione dell'algoritmo: ad esempio si assegni a $H(x)$ il tempo medio necessario a calcolare l'hash della stringa x e $C(X,Y)$ il tempo medio per comparare tra loro due stringhe, si può stimare il tempo di calcolo come $T_{comp}=H(K)+C(N,K)$ \footnotemark[1] dove K è l'insieme delle password e N è l'insieme di coppie utente-hash nel file del database. Analogamente il tempo richiesto per effettuare le operazioni di comunicazione, in questo caso sono le operazioni di caricamento dei file, può essere stimato come $T_{comm}=L(K) + L(N)$ dove $L(X)$ è il tempo medio per caricare una stringa dal disco fisico alla RAM, teoricamente bisognerebbe anche stimare il tempo necessario per il trasferimento dalla RAM alla cache, per tenere la trattazione semplice si eviterà di specificarlo, considerando che confronto al tempo di caricamento dal disco o di trasmissione in una rete, questo tempo è piuttosto piccolo e contribuisce poco al computo del tempo di comunicazione. A questo punto si può calcolare il computation to communication ratio come $ccratio=\frac{T_{comp}}{T_{comm}} = \frac{H(K)+C(N,K)}{L(K)+L(N)}$.

\footnotetext[1]{Durante la trattazione si commetterà un piccolo abuso di notazione, le funzioni che accettano singole stringhe riportando i tempi medi d'esecuzione accetteranno anche insiemi di stringhe, per cui ad esempio $H(K)$ sarà il tempo medio necessario ad effettuare l'hashing di tutto l'insieme delle password}


\subsection{Ricerca Lineare con architettura main worker}
L'architettura più semplice a cui si può pensare è sostanzialmente la classica main-worker, in cui più nodi , detti worker, che eseguono i task, in questo caso il confronto tra stringhe, vengono coordinati nelle loro operazioni da un main che distribuisce loro i dati su cui i task vengono effettuati. In pseudocodice si traduce facilmente in 

\begin{lstlisting}
    database = load_database()
    password = load_password()
    foreach pw in password do in parallel{
        pwhash = hash(pw)
        if pwhash in database{
            notify_password(pw)
        }
    }
\end{lstlisting}
L'unico problema è che non si sta tenendo conto di una caratteristica fondamentale del sistema in cui si sta lavorando: il bisogno dei nodi di comunicare. Il problema infatti sorge quando si considera che in qualche modo tutti i nodi dovranno avere conoscenza o delle password che si vogliono cercare oppure del database copiato, viste le dimensioni, l'approccio più semplice è sicuramente quello di distribuire a tutti i nodi una copia delle password da cercare mentre si divide a pezzi il database e lo si trasmette ai vari nodi che dovranno eseguire il task, questo supponendo che il file del database sia molto più grande di quello con le password da testare. Alla luce di queste considerazioni si può modificare un pò lo pseudocodice nel seguente modo 

\begin{lstlisting}
    rank = world().rank 
    if rank is root{
        database = load_database()
        password = load_password()
        broadcast(password, password.size)
        scatter(database, database/world.size)
    }
    else{
        password
        broadcast(password, password.size)
        database 
        scatter(database, database/world.size)
        foreach pw in password{
            pwhash = hash(pw)
            if pwhash in database{
                notify_password(pw)
            }
        }
    }
\end{lstlisting}
questa versione statica dell'algoritmo , divide il file in chunk di uguale lunghezza e li trasmette a tutti i nodi coinvolti, che cominciano il loro computo una volta che hanno ottenuto il file.

    \caption{Architettura main worker proposta per il problema}
\end{figure}

Lo svantaggio è che i nodi in quel frangente non faranno nient'altro se non aspettare che la trasmissione dei dati sia completa, di fatto però la sua implementazione è molto semplice, per cui vale la pena almeno a titolo conoscitivo di sapere in che misura scala bene sul problema. 
\subsubsection{Speedup, efficienza e ccratio}
Supponendo di assegnare le seguenti variabili 
\begin{itemize}
    \item P : il numero di esecutori 
    \item $S(X)$: il tempo necessario a trasmettere un elemento da un nodo all'altro, che è dipendente dalla dimensione dell'elemento 
    \item $T_{l}$ : il tempo di latenza medio tra due nodi (RTT). Tipicamente per una rete a 25 GB/s è di 10 $\mu s$
\end{itemize}
Si può derivare il tempo di comunicazione $T_{comm}(P,N,K)=L(K)+L(N)+2*T_{l}*P +S(K)+S(\frac{N}{P})*P$ e il tempo di computazione effettivo 
$T_{comp}(P,N,K)=\frac{H(K)}{P}+C(\frac{N}{P},K)$ da cui si può ottenere il tempo totale di esecuzione
$$ 
T(P,N,K)=L(K)+L(N)+2*T_{l}*P+S(K)*P+S(\frac{N}{P})*P + \frac{H(K)}{P}+C(\frac{N}{P},K)
$$ Per semplificare la trattazione, si considererà solo la dimensione del database, tenendo un insieme K fisso per le password. Da qui si possono ricavare diverse misure già a livello teorico :
\begin{itemize}
    \item CC Ratio: $\frac{T_{comp}}{T_{comm}}=\frac{\frac{H(K)}{P}+C(\frac{N}{P},K)}{L(K)+L(N)+2*T_{l}*P +S(K)+S(\frac{N}{P})*P}$
    \item Efficiency: $\frac{T(P,N,K)}{P}$
\end{itemize}
A questo punto si possono introdurre delle variabili aggiuntive, utili alla stima dei tempi
\begin{itemize}
    \item Lunghezza media di una password : 16 caratteri 
    \item Velocità della rete : 25 GB/s 
    \item Velocità del disco fisso: 700 MB/s 
    \item Velocità del core di un processore: 2.3 GHz 
    \item Dimensione dell'hash : 32 byte 
    \item Algoritmo di hashing SHA256: circa $0.81*10^{-3} s$ per stringa
\end{itemize}

La lunghezza media delle password è esagerata, ma è stata scelta in modo da coprire anche quei database su cui è stata posta una policy molto stringente in termini di lunghezza delle password. Bisogna fare un appunto, tendenzialmente più la policy è stringente , più le password saranno "semplici" dal punto di vista della conformazione perchè l'utente medio fatica a ricordarle. La velocità della rete è presa direttamente dal sito di hpc4ai che riporta la velocità della ethernet di connessione tra i nodi, la velocità del disco fisso è stimata considerando che il cluster usi degli HDD di tipo enterprise con interfaccia SAS, che normalmente riescono in lettura a offrire un range di velocità che varia dai 250 MB/s a 1GB/s. La velocità del processore invece è stimata partendo dalla velocità base di un Intel Xeon E5-2697V4 , un architettura disponibile per i formati server. La velocità di esecuzione di SHA256 è stata calcolata eseguendo un piccolo benchmark su 100000 stringhe su un processore AMD Ryzen 9-5950X, impostando una frequenza fissa a 2.3 GHz, si è ottenuta un massimo di $0.81*10^{-3} s$ necessari per calcolare l'hash su di una stringa, si potrebbe usare la media , che è decisamente più bassa $0.28*10^{-6} s$, ma vista la varianza del computo molto alta $1*10^{-s} s$ e vista la natura della simulazione che si preferisce sottostimi leggermente le performance dell'algoritmo, si opta per prendere il caso peggiore, visto che non si conosce la natura delle stringhe che generano questa varianza all'interno del calcolo.

Dal grafico si evince subito che l'algoritmo scala piuttosto bene all'aumentare dell'input e si dimostra anche piuttosto efficiente nonostante la sua semplicità. Di fatto in questa istanza non sono state considerate due cose, che potrebbero modificare profondamente il risultato di questa stima, il tempo di spostamento dalla RAM alla cache del processore quando avviene un cache miss e il tempo di lag dovuto alla preemption dei task eseguiti su una certa macchina, tutte variabili che richiederebbero una simulazione di un certo tipo più complicata e per cui normalmente è più efficace considerare invece i risultati di un benchmark diretto. 


Un ultima analisi va fatta considerando lo spazio che deve essere occupato in RAM per eseguire il processo. Per quanto vi sia la necessità di condividere uno dei due insiemi (il database e le password) in copia completa su tutti gli esecutori, a livello pratico bisogna tenere a mente che non è detto che tutti i task vengano eseguiti su macchine diverse per cui sono disponibili più strategie. Se si vuole mantenere la tecnologia di parallelizzazione omogenea, per cui si vuole usare solo MPI senza ricorrere al pthread per la parallelizzazione un utile metodo potrebbe essere quello di memorizzare la copia dell'insieme scelto, in questo caso quello delle password, in shared memory, così che tutti i task che vengono eseguiti sulla stessa macchina possano accedere a quel segmento senza per forza riceverne una copia da usare localmente al processo. Se invece si opta per l'utilizzo del multithread la memoria è già condivisa e quindi non è necessario ricorrere esplicitamente alla shared memory.


\subsection{Un architettura alternativa al main-worker}

Nel caso del main worker si è costretti a passare almeno uno dei due file in copie ai diversi nodi. A meno di non assicurarsi con metodi più o meno complicati, che ogni porzione del file di password sia stata comparata con ogni porzione del database in circolazione tra i nodi. In alternativa, si può adottare un'architettura con topologia ad anello ($N \to N+1 \pmod{P}$). In questo modello, il dizionario delle password viene suddiviso tra i nodi, mentre i blocchi del database "scorrono" attraverso la pipeline. Ad ogni stadio, un blocco di dati viene confrontato con il set di password locale, realizzando un confronto completo dopo un intero ciclo dell'anello.


\begin{figure}[H]
    \includegraphics[width=0.6\textwidth]{images/pipeline_diagram.png}
    \caption{Architettura ad anello}
\end{figure}

In questa architettura, il primo passo è distribuire le password da testare ai vari nodi, dopodichè si comincia distribuendo il primo frammento del database al primo nodo, che comincierà il processamento e lo passerà al nodo successivo. Esistono due momenti transitori in questa architettura, il primo è all'inizio , quando il primo frammento di database viene dato al nodo di testa che lo dovrà passare allo stadio successivo e così via, fintanto che questo frammento non avrà percorso tutta la pipeline i nodi che non lo hanno ancora ricevuto non saranno ancora attivi, alla fine invece si verificherà il processo opposto, ossia man mano che l'ultimo frammento di database attraversa l'anello i vari nodi si disattiveranno, sostanzialmente buttando via tempo di esecuzione. Nonostante questo difetto, che è fortemente dipendente dalla lunghezza della pipeline, si ottiene un vantaggio sostanziale in termini di spazio occupato dal database e dalle password perchè non bisogna distribuire una copia del secondo file a tutti i nodi , ma solo una porzione. In pseudocodice

\begin{lstlisting}
    rank = world().rank 
    if rank is root{
        password = load_password()
        database = load_database()
        datavector = split(database, world().size - 1)
        for i in 1..world.size() do{
            send(datavector[i],i)
        }
        tasks = split(password, world().size -1)
        for task in tasks do{
            send(task,rank+1,tasktoken)
        }
        send(rank+1,terminationtoken)
    }
    else{
        database = recv(root)
        while !terminationtoken{
            token = recv(rank-1)
            if token is tasktoken{
                for password in token.passwords do{
                    pwhash = hash(password)
                    if pwhash in database {
                        notify_password(password)
                    }
                }
                send(rank+1,tasktoken)
            }
            if token is terminationtoken{
                break
            }
        }
    }
\end{lstlisting}

Per capire meglio se questo approccio possa essere più o meno vantaggioso rispetto al precedente bisogna modellare opportunamente il problema, avendo cura di trattare il periodo transitorio, che può essere visto come una somma di tempi, se si prende $T_{task}$ come tempo impiegato da un nodo a completare un task, allora il transitorio iniziale sarà $\sum_{i=1}^{P-1}(P-i)*T_{task}*2=\frac{(p-1)p}{2}T_{task}*2$. Il tempo che un task impiega a essere completato è dipendente dai soliti parametri: la grandezza del database e la grandezza del file delle password, a meno che non sia decisa a priori la sua grandezza massima, configurazione che potrebbe essere utile per tenere sotto controllo il periodo transitorio iniziale, nell'ambito della simulazione per ottenere un'approssimazione teorica delle misure si considererà solo il caso in cui la lunghezza del task sia dipendente dal numero di esecutori e dalla dimensione del database.
\subsubsection{Speedup, efficienza e cc ratio}
Assumendo che il tempo per completare un task sia: $T_{task}=S(\frac{N}{P})*2+C(\frac{N}{P},\frac{K}{P})$ composto quindi soltanto dal tempo di ricezione e invio del task e dalla comparazione il tempo totale stimato si può scrivere come 

$$
T(P) =  \frac{(P-1)P}{2}*T_{task}+L(K)+L(N)+S(K)+S(N)+T_{task}
$$
