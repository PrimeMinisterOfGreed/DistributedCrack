\section{Attacco con ricerca lineare}

In un attacco di tipo password spraying esistono due entità, il database e il file con le password da testare, che vanno confrontati tra di loro. L'operazione di confronto è molto simile a un operazione di ricerca, infatti il database può essere visto come una lista utente-passwordhash per cui si vuole rispondere alla domanda: "Il database contiene uno o più hash uguali alla password che si sta esaminando?". Per rispondere a questa domanda bisogna eseguire queste operazioni: 
\begin{itemize}
    \item Caricare in memoria il file del database 
    \item Caricare in memoria il file delle password
    \item Calcolare l'hash della password correntemente in esame 
    \item Per ogni coppia nella lista del database controllare se esistono uno o più hash che corrispondono a quella password (al suo hash)
\end{itemize} 



Sia $H(x)$ il tempo medio necessario a calcolare l'hash della stringa x e $C(X,Y)$ il tempo medio per comparare tra loro due set di stringhe, allora il tempo totale per effettuare le operazioni di calcolo sarà $T_{comp}=H(K)+N*K$ dove K è il numero delle password nel file delle password e N è il numero di coppie utente-hash nel file del database. Mentre quello per effettuare le operazioni di caricamento sarà $T_{comm}=L(K) + L(N)$ dove $L(X)$ è il medio per caricare una stringa dal disco fisico alla RAM,\footnotemark[1] che essendo considerevolmente più alto rispetto al tempo di trasferimento dalla RAM alla cache della CPU, può essere usato come unico parametro di riferimento per quantificare il tempo di trasmissione totale. A questo punto si ottiene facilmente il computation to communication ratio di questa soluzione che è $ccratio=\frac{T_{comp}}{T_{comm}} = \frac{H(K)+C(N,K)}{L(K)+L(N)}$.

\footnotetext[1]{Per sintesi verranno riportati i tempi medi cumulati nella forma $L(K)=\sum_{i}L(K_{i})$}


\subsection{Ricerca Lineare con architettura main worker}
Dovendo effettuare una comparazione, si può distribuire il file con le password a tutti i nodi e dividere in P parti, quanti sono gli esecutori, il file del database. A questo punto idealmente  il file del database viene distribuito in modo statico, o in modo dinamico. Nel primo caso significa che all'inizio verranno trasmessi $(P*N)/P=N$ bytes per distribuire il database e $P*K$ per distribuire le password da testare, per poi cominciare ad eseguire gli $(N/P*K)$ confronti, in termini di complessità non ci si è allontanati molto dal caso base purtroppo, ma la cosa peggiore di questo metodo è che all'inizio presuppone di saturare molto l'I/O dei vari nodi per scambiarsi il file senza fare nient'altro, che può comportare uno spreco di tempo non indifferente. Nel secondo caso, la situazione migliora già notevolmente, ipotizzando un architettura main-worker infatti, il main divide il file in pezzi equi spaziati che i worker richiedono ogni volta che finiscono la computazione su uno, bisogna comunque distribuire all'inizio le copie delle password da testare, per cui la complessità computazionale e lo spazio occupato non cambiano rispetto al caso precedente, ma almeno la trasmissione del database e il confronto avverranno parallelamente.

Supponendo di aver completato la parte iniziale di scambio del file con le password da testare, rimane solo più il file del database, che può essere suddiviso e scambiato con i nodi su richiesta, sotto forma di Task. Ogni qualvolta il worker è vuoto chiede al nodo root un task, questo può essere o una coppia di indici, nel caso in cui ad esempio il file sia condiviso tramite clustered filesystem, oppure direttamente un array di stringhe qual'ora questo meccanismo non sia disponibile. Ogni qualvolta un worker trova una delle password nella porzione di file che gli è stata assegnata, questi lo notifica al nodo Root che rimane in attesa di questa tipologia di messaggi, e registra il risultato che alla fine della computazione verrà mostrato all'utente.

\subsubsection{Speedup, efficienza e ccratio}
Prendendo in esame il caso iniziale sequenziale è possibile aggiungere alcune variabili per ottenere un modello che descriva un caso con più esecutori 
\begin{itemize}
    \item P : il numero di esecutori 
    \item $S(X)$: il tempo necessario a trasmettere un elemento da un nodo all'altro, che è dipendente dalla dimensione dell'elemento 
    \item $T_{l}$ : il tempo di latenza medio tra due nodi (RTT). Tipicamente per una rete a 25 GB/s è di 10 $\mu s$
\end{itemize}
Introducendo queste variabili, si può modellare il tempo di esecuzione come 
$$
T(P,N,K)=L(K)+L(N)+2*T_{l}*P+S(K)*P+S(\frac{N}{P})*P + \frac{H(K)}{P}+C(\frac{N}{P}*K)
$$. Per semplificare la trattazione, si considererà solo la dimensione del database, tenendo un K fisso per le password. A questo punto si possono introdurre delle stime all'interno del modello e effettuare una simulazione. 
\begin{itemize}
    \item Lunghezza media di una password : 16 caratteri 
    \item Velocità della rete : 25 GB/s 
    \item Velocità del disco fisso: 700 MB/s 
    \item Velocità del core di un processore: 1.8 GHz 
    \item Dimensione dell'hash : 32 byte 
    \item Tempo medio di hashing per stringa : 2.7e-8 s 
    \item Algoritmo di hashing SHA256
\end{itemize}

\subsection{Un architettura alternativa al main-worker}

Nel caso del main worker si è costretti a passare almeno uno dei due file in copie ai diversi nodi. A meno di non assicurarsi con metodi più o meno complicati, che ogni porzione del file di password sia stata comparata con ogni porzione del database in circolazione tra i nodi. In alternativa, si può adottare un'architettura con topologia ad anello ($N \to N+1 \pmod{P}$). In questo modello, il dizionario delle password viene suddiviso tra i nodi, mentre i blocchi del database "scorrono" attraverso la pipeline. Ad ogni stadio, un blocco di dati viene confrontato con il set di password locale, realizzando un confronto completo dopo un intero ciclo della pipeline.

\begin{figure}[H]

    \caption{Architettura ad anello}

In questa architettura, il primo passo è distribuire le password da testare ai vari nodi, dopodichè si comincia distribuendo il primo frammento del database al primo nodo, che comincierà il processamento e lo passerà al nodo successivo. Esistono due momenti transitori in questa architettura, il primo è all'inizio , quando il primo frammento di database viene dato al nodo di testa che lo dovrà passare allo stadio successivo e così via, fintanto che questo frammento non avrà percorso tutta la pipeline i nodi che non lo hanno ancora ricevuto non saranno ancora attivi, alla fine invece si verificherà il processo opposto, ossia man mano che l'ultimo frammento di database attraversa l'anello i vari nodi si disattiveranno, sostanzialmente buttando via tempo di esecuzione. Nonostante questo difetto, che è fortemente dipendente dalla lunghezza della pipeline, si ottiene un vantaggio sostanziale in termini di spazio occupato dal database e dalle password perchè non bisogna distribuire una copia del secondo file a tutti i nodi , ma solo una porzione. \\ 
Per capire meglio se questo approccio possa essere più o meno vantaggioso rispetto al precedente bisogna modellare opportunamente il problema, avendo cura di trattare il periodo transitorio, che può essere visto come una somma di tempi, se si prende $T_{task}$ come tempo impiegato da un nodo a completare un task, allora il transitorio iniziale sarà $\sum_{i=1}^{P-1}(P-i)*T_{task}*2=\frac{(p-1)p}{2}T_{task}*2$. Il tempo che un task impiega a essere completato è dipendente dai soliti parametri: la grandezza del database e la grandezza del file delle password, a meno che non sia decisa a priori la sua grandezza massima, configurazione che potrebbe essere utile per tenere sotto controllo il periodo transitorio iniziale.
