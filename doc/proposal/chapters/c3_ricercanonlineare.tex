\section{Attacco con ricerca non lineare}

Un alternativa ai confronti lineari può essere quella di usare strutture dati che fanno uso in qualche modo dell'hashing per indirizzare correttamente le stringhe. Nel caso più semplice , si può usare una hashmap, in cui si possono allocare le stringhe del database intepretando gli hash SHA256 come numeri Big Int e poi sfruttando l'aritmetica modulare si possono posizionare a opportuni indirizzi di questa struttura. Una volta effettuata questa operazione si può eseguire l'hashing delle password da cercare e individuare con lo stesso procedimento se questa è contenuta o meno nella hashmap. 

\subsection{Un semplice caso sequenziale}
Il caso sequenziale a singolo nodo, implementa in modo molto semplice i passi descritti precedentemente, un possibile pseudocodice 

\begin{lstlisting}
    const space = I in (0,inf) // dimensione della hashmap decisa durante la compilazione
    database = load_database()
    password = load_password()
    map = hashmap(space)
    for i in 0..database.len do{
        index = bigint_read(hash) % space 
        map.append(index,{database[i].user,database[i].hash})
    }
    for pw in password do{
        pwhash = hash(pw)
        index = bigint_read(pwhash)%space 
        if map.contains(pwhash,index){
            notify_password(pw)
        }
    }
\end{lstlisting}

Per valutare le prestazioni di questa soluzione bisogna cambiare la funzione comparazione $C(X,Y)$, poichè gli accessi in una hashmap non sono più lineari. In questo caso infatti bisogna tenere in considerazione il numero di collisioni medie dato dalla dimensione dell'hashmap stessa, nello specifico di quanti buckets contiene. Questo valore si può scrivere come 
$E[O]=K-H_s +H_s *(\frac{H_s -1 }{H_s})^{K}$ dove $H_s$ sono gli spazi disponibili nella hashmap. In sostanza questo valore dice quanto sarà lunga la lista da ispezionare una volta eseguito l'accesso diretto, a questo punto  si può descrivere il runtime come 
$$
T_{seq}= C_h(N,K,H_s)+ H(K) + L(K) + L(N) + I(N) + I(K)
$$
dove:
\begin{itemize}
    \item $C_h(N,K,H_s)=$: è il numero di operazioni che bisogna eseguire in una hashmap con grandezza $H_s$ per comparare i due insiemi
    \item $I(X)$ : è il numero di operazioni necessario per trasformare un hash SHA256 in un BigInt e calcolarne il modulo, la prima operazione richiede pochi cicli, giusto per copiare l'hash, nel secondo caso invece la complessità è pari al quadrato del numero di bit, tuttavia esistono istruzioni specializzate AVX2 che , nel caso dei numeri a 256 bit , si è stimato empiricamente riducano il costo di questa operazione a circa 100 cicli.
\end{itemize}
 In questa casistica vale la pena pensare allo spazio che si stima venga occupato, poichè è richiesto che tutto il database venga in qualche modo caricato in memoria a differenza dei casi precedenti, dove invece è possibile ad esempio creare uno stream continuo tra lo storage e i nodi in modo da dover caricare solo porzioni più piccole di questi file così grandi. Questa funzione che rappresenta lo spazio occupato si può scrivere come  
$M_{seq}=N*SHA_{size}+K*SHA_{size}+H_s*8$, dove $SHA_{size}$ è la quantità di byte necessaria per memorizzare un singolo hash nell'algoritmo scelto, nel caso di SHA256 è 32 byte, $H_s$ è la dimensione della hashmap che va moltiplicata per la dimensione di un puntatore , nel caso di un architettura a 64 bit è 8 byte. Ad esempio se si volesse eseguire il test su un database con $10^6$ chiavi contro un file di 10000 chiavi, usando una hashmap grande il doppio del database , si occuperebbe uno spazio di 
$M=10^6*32+10^4*32+2* 10^6*8\approx46.6_{MB}$  che è uno spazio del tutto gestibile da un qualunque computer moderno, ma si evince bene già subito che non appena si sale di anche solo un ordine di grandezza la quantità di dati cresce significativamente. 

\subsection{Attacco con HashMap distribuita}
Parallelizzare un attacco del genere non è immediato, neanche sfruttando un architettura main worker. Tuttavia un primo metodo piuttosto semplice è quello di usare una hash table distribuita. Questa particolare struttura dati si presta particolarmente bene alla costruzione di database distribuiti, le DHT possono essere statiche o dinamiche, nel primo caso i nodi presenti sono fissi, nel secondo invece possono essere aggiunti o rimossi. Data la natura dell'architettura su cui l'algoritmo verrà eseguito si possono usare DHT statiche, a meno di non voler utilizzare funzioni particolari di MPI come l'aggiunta dinamica dei nodi, ma non è questo il caso.

Per usare una DHT l'approccio prevede sempre un architettura main worker, ogni worker istanzia in memoria una normale hash table. Il main legge il file del database e calcola il modulo dell'hash a seconda di quanti nodi ci sono in rete, poi manda al nodo indicato dal risultato l'hash se è diverso da se stesso, altrimenti lo memorizza. Successivamente il nodo root scorre il file delle password ed effettua lo stesso processo con ogni entry e se lui o un altro nodo trovano una corrispondenza lo notificano , in pseudocodice

\begin{lstlisting}

    rank = world().rank 
    if rank is root{
        map = hashmap(size)
        password = load_password()
        database = load_database()
        for entry in database do{
            dest = big_int(hash) % world().size
            if dest is not root{
                send(hash,dest,database_tag)
            }
            else{
                index = big_int(hash) % size
                map.insert(index,entry.user,entry.hash)
            }
        }
        for pw in password do {
            pwhash = hash(pw)
            dest = big_int(pwhash) % world.size()
            if dest is not root{
            send(pw,dest,pw_tag)
            }
            else{
                entry = map[pwhash]
                if entry != null{
                    notify_password(pw,entry.user,entry.hash)
                }
            }
        }
    }
    else{
        map = hashmap(size)
        message = recv(root)
        if message.tag is database_tag{
            index = big_int(message.hash)%size
            map.insert(message.hash,index)
        }
        else {
            pw = message.pw 
            hashpw = hash(pw)
            entry = map[hashpw]
            if entry != null{
                notify_password(pw,entry.user,entry.hash)
            }
        }
    }
\end{lstlisting}

Per ricavare le misure di performance si possono usare tutte le variabili del caso precedente, per cui si può scrivere
$$
T_{comp}= C_h(N,K,H_s*P) +  H(K)  + I(N) + I(P)
$$

Il vantaggio sostanziale per cui è che si abbassa notelvolmente la probabilità di collisioni nelle hashmap, di contro si aggiunge un overhead dovuto alla comunicazione, che però è ottimizzata poichè si conosce già il nodo possibile detentore di una certa password.
$$
T_{comm} =  L(K) + L(N) + S(N)+S(K)
$$

Questo approccio mostra chiaramente che è più efficace quando il database è più piccolo, dato che si avranno meno collisioni è un risultato del tutto atteso. Inoltre bisogna osservare che questa soluzione non è ottima per un architettura HPC, non si è introdotto nessun parallelismo a livello di computazione, si è solo distribuito lo spazio. Tuttavia potrebbe essere un buon metodo se il cluster presenta un nodo con prestazioni decisamente superiori agli altri, che vengono usati solo per poter memorizzare più dati in RAM di quanto si potrebbe fare con un nodo solo.  

\section{Conclusioni}

Non esiste un vincitore assoluto in questa lista di soluzioni, di fatto la scelta tra un approccio o l'altro varia molto in base alle caratteristiche dell'hardware che si sta considerando. Sicuramente la soluzioni peggiore invece è l'anello con numero di task fissi, che non offre uno speedup comparabile e non offre nessun vantaggio collaterale nell'usarlo.

Le altre tecniche invece potrebbero dimostrarsi valide a seconda dei contesti specifici, ad esempio la pipeline con task di dimensione fissa, anche se sembra nettamente inferiore in quanto a scalabilità rispetto alla soluzione master worker, presenta il vantaggio di poter trattare stream infiniti con estrema facilità. Invece la tecnica della hashmap distribuita potrebbe, allo stato attuale, essere efficace nel gestire lo stesso problema in un contesto con capacità computazionale limitata ma tanta memoria, a meno di non parallelizzare alcune delle sue fasi, che la renderebbero sicuramente più efficace. Bisogna inoltre specificare che le simulazioni numeriche sono molto approssimate, pertanto per effettuare uno scrutinio più approfondito e sperimentare se le soluzioni sono o meno adatte a un certo hardware sarà necessario effettuare dei veri e proprio benchmark.
